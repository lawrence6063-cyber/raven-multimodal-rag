Modular RAG MCP Server 数据流深度教学

从一个 PDF 被喂进来，到一句带 [n] 引用的答案吐回客户端 —— 追踪数据在 7 大模块间流转的完整旅程

这份文档要解决的问题：读完后，你应该能闭着眼睛口述——"当一个文档被 ingest 进来时，它变成了什么形状、经过哪些函数、最终落在哪里；当 MCP 客户端调用 query_knowledge_hub 时，一句话怎么变成向量、怎么和 BM25 融合、怎么变回一段带引用的 Markdown"。

这个项目是什么

Modular RAG MCP Server 是一个模块化、可插拔、可观测的检索增强生成（RAG）服务，对外通过 MCP（Model Context Protocol）以 stdio JSON-RPC 暴露 4 个工具，让任何 MCP 客户端（如 Claude Desktop）把"自己的知识库"接进来。它做两件事：

  • 写（Ingestion）：把文档切块、精炼、富化、编码成稠密+稀疏双向量，存进 Chroma + BM25 索引。
  • 读（Retrieval）：对一句查询做混合检索（语义 + 关键词 + RRF 融合 + 可选重排），返回带引用的答案；可选开启 Agentic RAG 让服务端 LLM 自主路由、分解、多跳、自省、合成。

① 前置知识 · 6 个核心数据类型

整个系统就是这几种数据结构在变形、流动、配对。前四个是"单一真相源"，定义在零业务依赖的 src/core/types.py；后两个是对外响应/Agent 的聚合产物。

Document —— 一份被解析好、等待切块的文档

由 Loader 产生（如 markitdown 把 PDF 转成纯文本），被 Splitter / Transform 消费。它是摄取管道的"入口形状"。

@dataclass
class Document:
    id: str
    text: str
    metadata: dict[str, Any] = field(default_factory=dict)
    # collection 等信息后续被写进 metadata["collection"]

Chunk —— 从 Document 切出来的一个文本块

由 Splitter 产生，被 Transform（精炼/富化/图像描述）就地增强，再被 Encoder 消费。source_ref 指回父 Document.id。

@dataclass
class Chunk:
    id: str
    text: str
    metadata: dict[str, Any] = field(default_factory=dict)
    source_ref: str = ""  # 父 Document.id

ChunkRecord —— 算好向量、可入库的块 最关键

由 Encoder 产生，被 VectorUpserter / BM25Indexer 消费。它同时携带稠密向量和稀疏向量，这正是"混合检索"在写入侧的根基。

@dataclass
class ChunkRecord:
    id: str
    text: str
    metadata: dict[str, Any] = field(default_factory=dict)
    dense_vector:  list[float]       = field(default_factory=list)  # 语义向量
    sparse_vector: dict[str, float] = field(default_factory=dict)  # term → 权重
双向量并存（理解的关键）：同一个块既有 dense_vector（喂向量库做语义相似）又有 sparse_vector（喂 BM25 做关键词匹配）。写入时两条索引各取所需；读取时两路结果再用 RRF 融合。整个"Hybrid"哲学就压缩在这一个数据结构里。

RetrievalResult —— 检索侧贯穿全程的"结果原子"

被 DenseRetriever / SparseRetriever / RRFFusion / QueryReranker 全程传递。注意 text 默认为空——Sparse 路只返回 chunk_id + score，全文由 HybridSearch 事后补齐。

@dataclass
class RetrievalResult:
    chunk_id: str
    score: float
    text: str = ""          # Sparse 路先留空，_fill_missing_text 补全
    metadata: dict[str, Any] = field(default_factory=dict)

MCPToolResult —— 对外的"双通道"响应

由 ResponseBuilder 产生，最终被 server.py 转成 SDK 的 CallToolResult。两个通道：content[0] 是人类可读 Markdown（含 [n] 标记），structured_content.citations 是机器可读结构化引用。

# src/core/response/mcp_types.py
MCPToolResult {
    content: list[TextContent | ImageContent]  # Markdown + 可选 Base64 图片
    structured_content: dict                       # {query, citations[], answer?, fallback?}
    is_error: bool
}
为什么双通道？低能力客户端只认 content 纯文本也能看到引用；高能力客户端可解析 structured_content.citations 做高亮跳转。一份响应同时照顾两端。

AgentResult —— Agentic 管道的聚合产物

由 AgenticRAG.run() 产生。answer 是服务端合成答案，results 用于引用，steps 记录每步决策，fallback 标记是否降级。

@dataclass
class AgentResult:
    answer: str = ""
    results: list[RetrievalResult] = field(default_factory=list)
    steps: list[dict] = field(default_factory=list)
    fallback: bool = False  # True = 降级为单次混合检索

② 全局数据流总览 · 两条管道

这个系统只有两条主数据流。记牢它们，所有细节都是挂在这两条骨架上的肉。

管道 A（写 / Ingestion）：File → Document → List[Chunk] → List[ChunkRecord](dense+sparse) → Chroma + BM25 索引
管道 B（读 / Retrieval）：query/image → ProcessedQuery → Dense+Sparse → RRF Fused → (rerank) → RetrievalResult → MCPToolResult
flowchart TB subgraph A["管道 A · 摄取（离线 scripts/ingest.py）"] F["File PDF/MD/图片"] --> L["Loader.load"] L --> D["Document"] D --> SP["DocumentChunker.split_document"] SP --> CK["List Chunk"] CK --> TR["Transform refine+enrich+caption"] TR --> EN["BatchProcessor.process dense+sparse"] EN --> CR["List ChunkRecord"] CR --> UP["VectorUpserter.upsert"] CR --> BM["BM25Indexer.build"] UP --> CH[("Chroma 向量库")] BM --> PK[("bm25 index.pkl")] end subgraph B["管道 B · 检索（在线 MCP 工具调用）"] Q["query / image"] --> HS["HybridSearch.search"] CH -.读.-> HS PK -.读.-> HS HS --> RR["List RetrievalResult"] RR --> RK["QueryReranker.rerank 可选"] RK --> RB["ResponseBuilder.build"] RB --> MR["MCPToolResult Markdown+citations"] end A -.写入索引，被 B 读取.-> B
对称之美：管道 A 的终点（Chroma + BM25）正是管道 B 的起点。写入侧造的"双向量"，读取侧用"双路检索 + RRF"对称地消费。理解这种对称，就理解了 Hybrid RAG 的全部。

③ 分层依赖架构

项目遵循"SDK 无关纯 Python 核心 + 薄 SDK 适配层"。依赖只能从外向内单向流动，最内层 core/types 零业务依赖，杜绝循环引用。

为什么 protocol_handler.py 要零 SDK 依赖？这样它能在没装 mcp SDK 的环境里被离线单测。JSON-RPC 错误码、参数校验、工具路由全部纯 Python；server.py 只是把 SDK 的 stdio 回调"翻译"进 ProtocolHandler。这是"可测试性优先"的典型设计。

④ 管道 A · 摄取六阶段逐步拆解

入口是 IngestionPipeline.run(file_path, collection, force, on_progress, trace)（src/ingestion/pipeline.py）。它把一个文件变成入库向量记录，共 6 个阶段。

1

integrity_check —— 去重闸门

SQLiteIntegrityChecker.compute_sha256(path) 算文件哈希；若 should_skip(file_hash) 为真且非 force，直接返回 {"status":"skipped"}。保证同一文件不被重复摄取。成功/失败最终 mark_success/mark_failed 记账。

2

load —— 文件 → Document

self._loader.load(str(path))（Loader 由 LoaderFactory.create(settings.loader) 产出，默认 markitdown）。随后 document.metadata["collection"] = collection，后续检索的 collection 过滤就靠它。

3

split —— Document → List[Chunk]

DocumentChunker.split_document(document)（Splitter 工厂，默认 recursive 递归字符切分）。每个 Chunk 的 source_ref 指回父文档。trace 记录 chunks=len(chunks)。

4

transform —— 三连就地增强（refine + enrich + caption）

三个 Transform 依次对 List[Chunk] 做 .transform(chunks)，链式返回新列表：

  • ChunkRefiner.transform：清洗/精炼文本。
  • MetadataEnricher.transform：补充元数据（标题、关键词等）。
  • ImageCaptioner.transform：对块内图片用 VisionLLM（qwen-vl-max）生成描述，写进 metadata["image_captions"]。

trace 阶段名 transform，method 固定 "refine+enrich+caption"。

5

encode —— Chunk → List[ChunkRecord]（双向量 + 图像向量）

BatchProcessor.process(chunks) 按 batch_size 分批：DenseEncoder 调 embedding API 算稠密向量，SparseEncoder 本地计算 tf 归一化得稀疏向量，合并成 ChunkRecord。随后 ImageEncoder.encode_document(...) 把文档内图片编码进共享多模态向量空间，追加为额外 ChunkRecord（records.extend(image_records)）。

6

store —— upsert + BM25 双写

VectorUpserter.upsert(records)：ChunkRecord → VectorRecord 写进 Chroma（跳过没有 dense_vector 的记录）。BM25Indexer.build(records)：增量合并、重算 IDF、pickle 持久化。最后 mark_success 记账，trace method="chroma+bm25"。

两套阶段名，有意区分：on_progress 回调用面向用户的阶段名（integrity_check/load/split/transform/encode/store），trace 记录用更技术化的名字（load/split/transform/embed/upsert）。前者给人看进度，后者给可观测算耗时。
源码骨架：IngestionPipeline.run() 的 try/finally 结构 
try:
    document = self._loader.load(...)                   # load
    chunks   = self._chunker.split_document(document)   # split
    chunks   = self._refiner.transform(chunks)          # transform x3
    chunks   = self._enricher.transform(chunks)
    chunks   = self._captioner.transform(chunks)
    records  = self._batch_processor.process(chunks)    # encode
    records += self._image_encoder.encode_document(...)
    self._upserter.upsert(records)                      # store
    self._bm25.build(records)
    self._integrity.mark_success(file_hash, ...)
    return {"status": "success", "chunk_count": len(records), ...}
except Exception as e:
    self._integrity.mark_failed(file_hash, str(e))      # 记账失败
    trace.record_stage("error", method=type(e).__name__)
    raise
finally:
    if own_trace:                                       # 自己创建的 trace 才收尾
        trace.finish(); self._collector.collect(trace)

⑦ 管道 B · HybridSearch 逐步拆解

核心是 HybridSearch.search(query, top_k, filters, trace, image)（src/core/query_engine/hybrid_search.py）。它支持三种查询模式，每步都打 trace。

三种模式（跨模态路径 B）：
  • 纯文本：Dense(文本向量) + Sparse(关键词) + RRF（原始行为）。
  • 纯图像：只走 Dense(图像向量)；BM25 对图片无意义，跳过。
  • 文本+图像：Dense 用图像向量（视觉意图）驱动，Sparse 仍用文本关键词，再 RRF 融合。
1

query_processing —— query → ProcessedQuery

QueryProcessor.process(query, filters)：抽取关键词（中英停用词过滤）+ 解析 inline filter（如 collection:xxx），合并进 merged_filters。trace 记录 keywords。

2

dense_retrieval —— 语义召回（图像向量优先）

if image is not None:
    image_vector = self._dense.embed_image_query(image)   # 跨模态
    dense_results = self._dense.retrieve_by_vector(image_vector, ...)
elif query:
    dense_results = self._dense.retrieve(query, top_k=k, ...)

整段包在 try/except 里——Dense 失败不抛错，降级为只用 Sparse 继续。

3

sparse_retrieval —— BM25 关键词召回

仅当 processed.keywords 非空时 SparseRetriever.retrieve(keywords, top_k)。它只返回 chunk_id + score，text 留空。同样 try/except 降级。

4

fusion —— 四分支融合策略

if dense_results and sparse_results:
    fused = self._fusion.fuse(dense, sparse, top_k=k); method="rrf"
elif dense_results:  fused = dense[:k];  method="dense_only"
elif sparse_results: fused = sparse[:k]; method="sparse_only"
else:               fused = [];         method="empty"

两路都有才真正 RRF；只有一路就直接截断；都没有则空。融合方法名进 trace，方便事后诊断"为什么没结果"。

5

_fill_missing_text —— 给 Sparse 结果补全文

筛出 text 为空的 chunk_id，批量 self._store.get_by_ids(missing_ids) 回填全文与元数据。若全部已有 text 则跳过这次 IO；失败只警告不抛错。

6

_apply_metadata_filters —— 兜底元数据过滤

对不支持原生 filter 的向量库做事后过滤，最后 return fused[:k]。

QueryKnowledgeHubTool.run()（src/mcp_server/tools/query_knowledge_hub.py）串起全链路：

RRF（Reciprocal Rank Fusion）到底怎么算

公式：RRF_score(d) = Σ 1/(k + rank_i)，对文档 d 出现的每个结果列表累加，k=60（settings.retrieval.rrf_k）。
for results in result_lists:               # dense 列表、sparse 列表
    for rank, result in enumerate(results, start=1):
        rrf_score = 1.0 / (self._k + rank)  # 排名越靠前贡献越大
        scores[result.chunk_id] += rrf_score    # 跨列表累加
ranked = sorted(scores.items(), key=..., reverse=True)[:top_k]

为什么用 RRF 而非分数加权？Dense 的余弦相似度（0~1）和 BM25 分数（可能上百）量纲完全不同，无法直接相加。RRF 只看"排名"不看"原始分数"，天然免疫量纲差异，是混合检索的事实标准。

⑨ 检索类型变换链路

ResponseBuilder 把 RetrievalResult[] 交给 CitationGenerator.generate() 生成 1-based 引用（探测 source/page 多键，text 预览截 300 字符），再渲染成 ## Results for: "query" + 编号列表 + ### References 的 Markdown。空结果返回 _EMPTY_HINT 友好提示。

⑩ 增强路径 · Agentic RAG 五步闭环

当 settings.agent.enabled=True 时，agentic_query 工具不再直接返回段落，而是跑一个服务端自主智能体：

route → transform → (multi-hop retrieve → reflect)* → synthesize

核心是 AgenticRAG.run()（src/core/agent/agentic_rag.py）。它永不抛错：任何失败都被全局 try/except 降级为单次混合检索（fallback=True）。

flowchart TB Q["query"] --> RT{"① route QueryRouter.decide"} RT -->|need_retrieval=False 且有 direct_answer| DA["直接回答 AgentResult(answer)"] RT -->|需要检索| TF["② transform QueryTransformer.transform 分解子查询"] TF --> LOOP["③ 多跳循环 _retrieve_loop hop < max_hops"] LOOP --> RET["_retrieve(HybridSearch) → _maybe_rerank → _accumulate 去重累积"] RET --> REF{"④ reflect Reflector.assess sufficient?"} REF -->|不足 且有 follow_up 且 hop|足够 / 到达上限| SY["⑤ synthesize AnswerSynthesizer.answer"] SY --> AR["AgentResult answer+results+steps"] LOOP -.任何异常.-> FB["_fallback 单次混合检索 fallback=True"] RT -.异常.-> FB FB --> AR
步组件做什么失败时
①routeQueryRouterLLM 决定"是否检索 + 哪些 collection"（白名单校验）降级 retrieve-all，never raises
②transformQueryTransformer分解子查询，去重 + capped(max_subqueries)回退原始 query
③retrieveHybridSearch + Reranker多跳召回，_accumulate 按 chunk_id 去重保最高分循环有 max_hops/max_context_chunks 硬上限
④reflectReflectorCRAG/Self-RAG 充分性判定，不足给 follow_up_queries保守返回 sufficient=True（停止循环）
⑤synthesizeAnswerSynthesizerLLM 基于 numbered context 合成带 [n] 答案synthesize 关闭则 answer 空，只返回结果
所有循环都有硬上限：max_hops（默认 3）、max_context_chunks、max_reflect_rounds。而且 reflect 在最后一跳被跳过（hop < max_hops）——没有"行动空间"就不浪费一次 LLM 调用。这是防止 Agent 无限循环 / 烧 token 的工程纪律。
_accumulate 去重累积的精妙之处 
for r in results:
    existing = seen.get(r.chunk_id)
    if existing is not None:        # 已见过：只在更高分时替换
        if r.score > context[existing].score:
            context[existing] = r
        continue
    if len(context) >= max_chunks:    # 预算用尽：丢弃
        continue
    seen[r.chunk_id] = len(context); context.append(r); added += 1

跨多跳累积上下文，同一个 chunk 只保留最高分版本，且总量受 max_chunks 约束。返回新增命中数用于 trace。

⑫ MCP 协议层 · stdio JSON-RPC

对外只暴露 4 个工具。MCP 层分两半：纯 Python 的 ProtocolHandler（可离线单测）+ 薄 SDK 适配 server.py。

工具必填参数行为

ProtocolHandler：零 SDK 依赖的 JSON-RPC 路由

# PROTOCOL_VERSION = "2025-06-18"  SERVER_NAME = "modular-rag-mcp-server"
INVALID_REQUEST=-32600  METHOD_NOT_FOUND=-32601  INVALID_PARAMS=-32602  INTERNAL_ERROR=-32603

def handle_tools_call(self, name, arguments):
    spec = self._tools.get(name)
    if spec is None: raise JsonRpcError(METHOD_NOT_FOUND, ...)  # -32601
    self._validate_required(spec, args)                       # 缺参 → -32602
    try:
        result = spec.func(**args)
    except JsonRpcError: raise                            # 业务错误原样上抛
    except TypeError:   raise JsonRpcError(INVALID_PARAMS, ...)  # 错误参数
    except Exception:   raise JsonRpcError(INTERNAL_ERROR, ...)  # 不泄露堆栈
stdout 必须绝对干净：MCP 用 stdout 传协议消息，所以所有日志走 stderr，所有 trace 只写 logs/traces.jsonl，绝不 print 到 stdout——否则会污染 JSON-RPC 帧，客户端直接报错。这是 stdio transport 的铁律。

server.py 用 SDK 的 lowlevel.Server + @list_tools/@call_tool 把回调接到 ProtocolHandler，_to_call_tool_result() 再把 dict 转成 SDK 的 CallToolResult（支持 ImageContent）。

⑬ 可插拔工厂 · 一次注册，到处替换

7 大能力（VectorStore / Embedding / LLM / Evaluator / Splitter / Reranker / VisionLLM）全部走同一套装饰器注册 + 惰性内建注册模式，配置里换个 provider 名就能切换实现。

# src/libs/vector_store/vector_store_factory.py
_VECTOR_STORE_REGISTRY: dict[str, type] = {}

def register_vector_store(name):           # 装饰器：注册一个实现
    def deco(cls): _VECTOR_STORE_REGISTRY[name] = cls; return cls
    return deco

class VectorStoreFactory:
    @staticmethod
    def create(settings):
        _ensure_builtins_registered()             # 惰性导入内建实现，触发注册
        cls = _VECTOR_STORE_REGISTRY[settings.provider]
        return cls(settings)
惰性注册的坑（项目记忆）：装饰器只有在模块被 import 时才执行。若工厂在 create() 里不主动 _ensure_builtins_registered() 把内建实现 import 一遍，注册表就是空的、provider 找不到。这是"装饰器注册模式"最常见的踩坑点。

所有实现都继承各自的 Base* 抽象基类（ABC）。例如 BaseVectorStore 约定 upsert/query/delete/get_by_ids/provider_name，并定义 VectorRecord/QueryResult/VectorStoreError 契约。编排层只依赖抽象，不依赖具体实现，这正是"模块化"的来源。

⑭ 多模态跨模态检索（路径 B）

项目用 DashScope multimodal-embedding-v1 把文字和图片编码进同一个 1024 维向量空间，于是"以文搜图 / 以图搜文 / 以图搜图"全都成立——它们在向量空间里本就是邻居。

flowchart LR subgraph 写入 IMG["文档内图片"] --> IE["ImageEncoder.encode_document"] IE --> IV["图像向量 ChunkRecord"] IV --> CH[("共享向量空间 Chroma")] end subgraph 检索 QI["查询图片"] --> EIQ["embed_image_query"] EIQ --> RBV["retrieve_by_vector"] RBV --> CH CH --> RES["RetrievalResult（可能是图片块）"] end

检索侧在 HybridSearch.search 里：传了 image 就用 embed_image_query 得到图像向量、走 retrieve_by_vector； 响应侧 MultimodalAssembler.assemble(results) 把命中块关联的图片读出来、转 Base64 ImageContent 追加进 content。

降级安全：多模态是"增强"，不是"必需"。图像 embedding 拿不到时 embed_image_query 返回空 → 记 warning、忽略图像查询；图片组装失败 → 只警告，文本答案照常返回。

⑮ 可观测 Trace 体系

每次 query / ingestion 执行都带一个 TraceContext，累积带时长的 stages，结束时由 TraceCollector 落盘成 JSONL。

# src/core/trace/trace_context.py
trace = TraceContext(trace_type="query")         # 或 "ingestion"
with trace.stage("dense_retrieval", method="openai"):  # 自动计时
    ...
trace.record_stage("fusion", method="rrf", results=12)  # 手动记一条
trace.finish()
collector.collect(trace)                          # enabled 时写 logs/traces.jsonl
设计点说明
只记轻量字段name/method/elapsed_ms + 计数/标志，绝不记密钥或原始 payload
永不破坏主流程TraceCollector.collect 内部 try/except 吞异常，trace 失败不影响检索/摄取
不污染 stdout只写 logs/traces.jsonl，保 MCP stdio 干净（见 ⑫）
谁创建谁收尾Pipeline 里 own_trace 标志决定是否 finish/collect，避免重复落盘

⑯ 降级哲学 · 贯穿全系统的交叉切面

如果只记住这份文档的一句话，记这句："增强功能失败一律降级，绝不崩溃"。它不是某个模块的特性，而是整个系统的设计信条。

位置失败场景降级行为
HybridSearchDense 召回异常只用 Sparse 继续（反之亦然）
QueryReranker重排模型不可用保持原序（rerank_fallback=True）
AgenticRAG任何环节抛错全局降级为单次混合检索（fallback=True）
QueryRouter路由 LLM 失败降级 retrieve-all，never raises
QueryTransformer子查询分解失败回退原始 query
Reflector充分性判定失败保守 sufficient=True，停止循环
MultimodalAssembler图片组装失败只警告，文本答案照常
TraceCollector落盘异常吞掉异常，主流程无感
配套的"硬上限"纪律：Agent 所有循环都有 max_hops / max_subqueries / max_context_chunks / max_reflect_rounds 上限。降级保证"不崩"，上限保证"不失控烧钱"。两者合起来，才是生产级 RAG 的安全网。
安全要点（贯穿）：
  • 图像输入白名单：validate_query_image 只接受 Base64 或 data/ 目录下的本地路径，防路径穿越。
  • API Key 仅环境变量：_resolve_api_keys 按 provider 从 DASHSCOPE/OPENAI/DEEPSEEK/AZURE 环境变量回退，密钥不入配置文件、不进 trace。
  • 错误不泄露堆栈：ProtocolHandler 把内部异常统一包成 -32603 "Internal error"。
